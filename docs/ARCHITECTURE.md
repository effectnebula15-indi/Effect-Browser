# Архитектура

Документ объясняет одно решение и его последствия: **почему Tor-контейнеры вынесены в
отдельный процесс ОС**. Всё остальное в проекте — обычный MVVM и следует из этого решения.

---

## 1. Контейнеры: изоляция хранилища

Это простая часть, и GeckoView делает её за нас.

Сессия создаётся с `contextId`:

```kotlin
GeckoSessionSettings.Builder()
    .contextId(container.contextId)   // ← вся изоляция хранилища здесь
    .build()
```

Gecko записывает это значение в origin-атрибут `geckoViewSessionContextId`. Origin-атрибуты
участвуют в ключе, по которому разделяются cookie, localStorage, sessionStorage, IndexedDB и
HTTP-кэш. Две сессии с разными `contextId` физически не видят данные друг друга — можно держать
два живых логина на один сайт одновременно.

`contextId` генерируется один раз (`UUID`) и хранится в Room навсегда. **Переиспользовать его
для другого контейнера нельзя** — новый контейнер получил бы чужую банку с cookie.

Удаление контейнера чистит и хранилище:

```kotlin
runtime.storageController.clearDataForSessionContext(contextId)
```

### Важная деталь про `contextId`

`geckoViewSessionContextId` — **не** `userContextId`. Это разные origin-атрибуты.
`userContextId` — механизм Contextual Identities десктопного Firefox; в GeckoView контейнеры
живут на своём атрибуте.

Последствие описано в §2.3.

## 2. Сеть на контейнер: в чём проблема

Требование: у контейнера есть флаг «обычное соединение» / «через Tor», и трафик его сессий
должен идти соответственно. Причём контейнеры обоих типов должны работать одновременно.

### 2.1 Чего нет

У GeckoView **нет** API прокси на уровне сессии. В `GeckoSessionSettings.Builder` нет ничего
сетевого — только `contextId`, `usePrivateMode`, `useTrackingProtection`, `userAgentMode`,
`viewportMode`, `allowJavascript` и подобное.

Прокси в Gecko задаётся исключительно preferences:

```
network.proxy.type          1 = ручная настройка
network.proxy.socks         127.0.0.1
network.proxy.socks_port    <порт>
network.proxy.socks_version 5
network.proxy.socks_remote_dns
```

Эти preferences — **глобальные для процесса Gecko**. Не для сессии, не для вкладки.

### 2.2 Почему нельзя «просто переключать префы»

Можно было бы менять `network.proxy.*` при переключении активного контейнера. Это ломается
сразу по двум причинам:

- фоновые вкладки продолжают грузить ресурсы, и они уедут в текущий (возможно чужой) прокси;
- любая гонка между сменой префа и запросом — это утечка, причём тихая.

Для функции, весь смысл которой в изоляции, «обычно работает» — не критерий.

### 2.3 Почему не WebExtension `proxy.onRequest`

Стандартный совет для Firefox: поставить расширение с `browser.proxy.onRequest` и решать
пофайрвольно, различая контейнеры по `requestDetails.cookieStoreId`.

На GeckoView **не сработает**: `cookieStoreId` отражает `userContextId`, а наши контейнеры
живут на `geckoViewSessionContextId` (см. §1). Расширение не сможет отличить контейнеры.

Теоретически можно завязаться на `tabId` и вести своё соответствие «tab → контейнер». Но:

- у запросов вне вкладки `tabId == -1`;
- надёжность соответствия зависит от полноты реализации tabs-модели в GeckoView;
- любой промах — тихая утечка в открытую сеть.

Отвергнуто: это критичный для безопасности путь, а он получается вероятностным.

### 2.4 Принятое решение: разделение по процессам

Два факта, вместе дающие ответ:

1. preferences прокси глобальны **для процесса**;
2. в процессе может существовать только **один** `GeckoRuntime`.

Значит, «контейнер прибит к Tor» надёжно выражается ровно одним способом: дать ему процесс, в
котором runtime **никогда** не был настроен на прямое соединение.

```
процесс по умолчанию            процесс :tor
├── MainActivity                ├── TorBrowserActivity
├── GeckoRuntime (без прокси)   ├── GeckoRuntime (SOCKS → tor)
└── контейнеры DIRECT           ├── демон tor (kmp-tor)
                                └── контейнеры TOR
             \                        /
              \                      /
               Room (общая БД, enableMultiInstanceInvalidation)
```

Это объявлено в `AndroidManifest.xml` и является частью модели угроз, а не оптимизацией:

```xml
<activity android:name=".ui.TorBrowserActivity" android:process=":tor" ... />
```

Переключение контейнера, который живёт в другом процессе, — это `startActivity`
(`BrowserEffect.SwitchProcess`). Для пользователя это просто тап по чипу.

Демон tor поднимается **в том же процессе `:tor`**, поэтому его SOCKS-порт передаётся в
Gecko напрямую, без IPC.

## 3. Fail-closed: чтобы «Tor не поднялся» не означало «пошли в открытую»

Самый опасный сценарий — не «не работает», а «работает, но мимо Tor». Защита слоями,
`gecko/GeckoProxyPrefs.kt`:

| Preference | Значение | Что закрывает |
|---|---|---|
| `network.proxy.failover_direct` | `false` | **Главное.** По умолчанию `true` — Gecko при недоступном прокси молча идёт напрямую. То есть «tor упал» превратилось бы в «браузер в открытой сети, никому не сказав». |
| `network.proxy.socks_remote_dns` | `true` | Резолв имён через tor. Без этого имя хоста утекает локальному DNS до всякого tor. |
| `network.proxy.no_proxies_on` | `""` | Ничего не исключается из прокси, включая RFC1918 и localhost. |
| `media.peerconnection.enabled` | `false` | WebRTC ходит по UDP мимо SOCKS и раскрывает реальные адреса. |
| `network.dns.disablePrefetch`, `network.predictor.enabled`, `network.prefetch-next`, `network.http.speculative-parallel-limit` | off / 0 | Спекулятивные соединения к тому, куда пользователь не переходил. |
| `browser.safebrowsing.*` | `false` | Иначе tor-процесс шлёт хеши URL в Google. |
| `network.captive-portal-service.enabled`, `network.connectivity-service.enabled` | `false` | Проверки связи стучатся на `detectportal.firefox.com`. |

Плюс два поведенческих правила:

1. **Blackhole до старта.** `GeckoProxyPrefs.applyBlackhole()` отрабатывает до первого
   рендеринга в `:tor` и указывает на порт, где никто не слушает. Вместе с
   `failover_direct = false` запрос до готовности tor не уходит никуда — он падает.

2. **Единственная точка навигации.** Всё, что грузит страницу, проходит через
   `BrowserViewModel.loadIfPermitted()`, а он проверяет `state.canNavigate`. Так новый
   вызов `loadUri` нельзя случайно добавить в обход проверки.

`TorStatus.Ready` требует **обоих** сигналов: `bootstrap == 100` и известный SOCKS-порт.
Только bootstrap недостаточно — порт мог ещё не подняться.

### Что этот дизайн НЕ даёт

Это не Tor Browser. Разделение процессов гарантирует маршрутизацию, но **не анонимность**:

- нет защиты от fingerprinting (letterboxing, спуфинг шрифтов/времени и т.п.);
- нет изоляции цепочек по first-party домену;
- нет уровней безопасности Tor Browser.

Если цель — противостоять анализу трафика и деанонимизации, это Tor Browser, а не данный
проект. Здесь Tor решает задачу «сменить сетевой путь для контейнера».

## 4. Данные

Room, три таблицы: `containers`, `bookmarks`, `tabs`.

Единственная нетривиальная деталь — **база общая для двух процессов**:

```kotlin
Room.databaseBuilder(...)
    .enableMultiInstanceInvalidation()
    .build()
```

Без этого запись в процессе `:tor` не инвалидировала бы живые запросы в основном процессе, и
каждый показывал бы свой устаревший список контейнеров.

`tabs` ссылается на `containers` с `onDelete = CASCADE`.

## 5. Известный хрупкий шов: `TorStartup`

kmp-tor получает Context приложения и находит `libtor.so` из инициализаторов
`androidx.startup`. Их запускает `androidx.startup.InitializationProvider`, объявленный в AAR
**без `android:process`** — то есть он существует только в процессе по умолчанию.

В процессе `:tor` он не отработает, и `TorServiceConfig.newEnvironment()` упадёт с null
Context. Объявить провайдер второй раз нельзя: manifest merger различает провайдеры по имени
класса и отвергает вторую запись с другим authority.

Решение — `tor/TorStartup.kt`: явный вызов
`AppInitializer.initializeComponent(TorServiceConfig$Initializer)`. API публичный, зависимости
инициализатора он подтянет сам. Сам класс приходится доставать рефлексией только потому, что
kmp-tor помечает его `internal` (в байткоде он public).

**Это самое хрупкое место проекта**: обновление kmp-tor может переименовать класс. Поэтому
там явный `IllegalStateException` с понятным текстом, а не тихий сбой.

## 6. Публикация в Google Play

Стоит решить до того, как вкладываться в публикацию.

- **Проксирующее поведение.** Приложение маршрутизирует трафик через локальный SOCKS. VPN
  API не используется и `BIND_VPN_SERVICE` не запрашивается, что снимает часть вопросов, но
  политика Play по приложениям с анонимизацией трафика применяется по существу, а не по
  формальному признаку.
- **Размер.** GeckoView + бинарники tor. ABI splits обязательны; при публикации — AAB.
- **Исполняемый код.** Выбран `resource-noexec-tor` (JNI), а не `exec`-вариант, который
  запускает бинарник как процесс. Для Play это заметно спокойнее.
- **Возрастной рейтинг / категория.** Браузер с доступом к произвольному контенту обычно
  требует отдельного внимания к рейтингу.

Если Play — цель, самая безопасная последовательность: сначала выложить F-Droid/APK-сборку,
и только потом идти в Play, уже имея работающий продукт, который не жалко переделать под
требования.
